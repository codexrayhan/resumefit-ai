Security

Last updated: October 2026

1. Our Security Approach

ResumeFit AI is designed with a simple, honest security model: process what you send, return the result, and keep as little as possible. Your resume file and text are never stored. Guests have no account and nothing is saved. If you sign in with Google, the app keeps only your basic profile details and your analysis scores. Sign-in is handled by Google, so the app never sees or stores a password. Signed-in users can view and delete only their own records.

All computation happens server-side in Python. The ML models — SBERT all-MiniLM-L6-v2, the LinearSVC classifier, and the TF-IDF vectorizers — are loaded from local .pkl files. No external API call is ever made during analysis.

2. File Handling

An uploaded file is written to a temporary location on the server only long enough for its text to be extracted — usually under a second. The temporary file and its folder are deleted immediately afterwards, whether or not extraction succeeds. The file is never kept, and the extracted text is never saved.

Flask enforces a hard upload limit of 5 MB per request. Any file exceeding this limit is rejected before processing begins.

File type is validated server-side by checking the file extension. Only .pdf, .docx, and .txt files are accepted. Any other extension is rejected with an error before any content is read. Uploaded file names are sanitized before they are used.

3. Data Transmission

In a local deployment, your resume file travels only from your browser to localhost. It never leaves your machine. Your resume and job description are not forwarded to any external server, cloud service, or third party during analysis. If you choose to sign in, your browser is redirected to Google to confirm your identity, and Google shares your name, email address, and profile picture link with the app. Your resume is never part of that exchange.

If the app is deployed to a remote server, the file upload travels over the network connection between your browser and that server. We recommend running the app over HTTPS in any network-accessible deployment.

4. Accounts and Sessions

Signing in is optional. When you sign in, authentication is handled by Google using OAuth 2.0 and OpenID Connect. The app never receives or stores your Google password.

On your first sign-in, the app creates an account record containing your Google account identifier, name, email address, and profile picture link. For each analysis you run while signed in, it saves the resume name and job title you entered, the match score, the missing keywords, the predicted roles, and a timestamp. Resume text and job descriptions are never saved.

The app uses a single session cookie. It is cryptographically signed with a secret key so it cannot be altered, it is not readable by page scripts (HttpOnly), and it is restricted to same-site requests (SameSite=Lax). For guests, the same cookie holds a counter of free analyses used.

Every request for history or for deleting data is checked against the signed-in account. A user can read and delete only their own records, and a request for someone else's record is answered as if it does not exist.

Account and history data are kept in a local database file on the server. The sign-in credentials and the session secret are supplied through environment variables and are kept out of version control. From the dashboard, a user can delete a single analysis or delete their account, which permanently removes the account record and all saved analyses.

5. What We Do Not Collect

We do not collect, store, or process any of the following:

  • Passwords or other authentication credentials
  • Payment or financial information
  • Phone numbers or postal addresses
  • The contents of your resume or job description
  • Device fingerprints, browser history, or behavioral analytics

The application does not record or use IP addresses. As with any web server, the server software may write standard access logs, which contain request lines but never resume content.

Guests provide no personal information at all. For signed-in users, the only personal data held is the Google profile information listed above, together with the analysis scores they chose to save.

6. Responsible Disclosure

If you discover a security vulnerability in ResumeFit AI, please report it responsibly. Do not publish details publicly before giving us a chance to address it.

Open a private or public issue on our GitHub repository and describe what you found. We will respond as quickly as we can.

7. Limitations

ResumeFit AI is a university course project, not a hardened production application. It has not undergone a formal security audit or penetration test.

Flask's built-in development server and debug mode must be disabled before any public-facing deployment. Running with debug=True in production exposes an interactive debugger that can execute arbitrary code. We strongly recommend using a production-grade WSGI server (such as Gunicorn) if you deploy this application beyond a local demo.

If you deploy the app with Google sign-in enabled, serve it over HTTPS, use a long random SECRET_KEY, and keep the .env file and the Google client secret out of version control. Also add your deployed address followed by /auth/callback as an authorized redirect URI in Google Cloud, and enable secure session cookies. The built-in SQLite database is suitable for a demo, but a larger deployment should use a managed database with regular backups.

The guest limit of two free analyses is tracked in a cookie, so it is a convenience limit rather than a security control. Clearing cookies resets it.
